# Integration and review rounds

Read when integrating a job, preparing or requesting a review round, or planning a fix round.

## Graded integration checks

Apply the expensive-check rules below before a formal review round. An individual review or a correction-verification message does not itself trigger a suite. At integration a full suite is needed only in the third and last cases below. The release step says when it runs at the release.

- A fast-forward to the tree the worker tested: check the diff scope only.
- A rebase that brings in only files the job does not own: run the job's tests, the repository-wide consistency tests (tests of the whole repository's registries and documentation references), the linter and the project's policy lints (its own lints of the source and the rendered documentation).
- A rebase that touches the job's code files, or that needed conflict resolution: run the full suite.
- A documentation-only change: verify its claims and actual consuming paths, and close authorized local corrections in the existing review. Confirm that executable code and runtime-consumed values are unchanged. Run required documentation checks on the assembled result, reusing applicable evidence. Execute examples when their executable content changed or their validity is uncertain. Pure prose edits do not trigger the library suite or a new fix round.
- A job that changes an entry point every extension passes through: the principal runs the full suite before integrating it.

Before a rebase, make a backup branch at the worker's final revision, and resolve conflicts from both sides' intent. Before a destructive Git operation in a shared clone, read `git reflog -3` and compare HEAD with the expectation. Log the integrated revision and results, and tell running jobs their new base. Avoid competing full suites on one machine. Assign an owner to each unresolved substantive obligation, keeping optional wording preferences out of the active ledger.

The gate reads every failed test line, not the count against the known-failure list. (NWQLib 1.0: a cross-job test staleness was fast-forwarded past once.) When one job changes a contract that another job's tests assert, merge the contract change first and rerun the other job's covering tests before its merge, or name the changed contract in the later brief's seams. Review integrated jobs while dependent jobs still run: a defect found there goes to the running owner instead of a follow-up.

Match verification targets to the actual delivery requirements. A command restricted to source files does not establish that notebooks, generated examples or other required formats pass. Run the project's canonical final checks on the integrated delivery surface, record any exclusions, and send omissions to the existing owner. Correcting the collection scope does not require another review layer.

## Before each formal round

- Run one full suite on each supported platform whose code path changed (see the expensive checks below), all platforms in parallel, unless one already ran on the same tree, dependencies and platform.
- The mathematics advisor checks only the mathematics the round changed, with its code: the changed items, the principal's decisions and the changed texts. It does not widen into mathematics the round did not touch.
- Before a review of fixes, the fix list gives each item with its disposition and commits, what each commit changes (code, tests or documentation), the owner and scope of each deferred item and who decided it (the user, or the principal and the counselor under the step 0 delegation), and the open questions. The reviewers check each entry against its commits. (NWQLib 0.99: a deferral recorded only in the principal's ledger, which the reviewers do not read, reached the review as an item without an owner.)

## The expensive checks

A full suite on a platform and the mutation campaign are the expensive checks. Wherever this skill calls for one, at an integration, before a review, at the release or for any change after the release checks, whether a fix of a late finding or work the user adds, the principal judges from the diff since the check's last run whether the change can alter its result, and a change that cannot leaves the last run standing. The integration grades and the before-review rule apply this at their steps. The principal takes the judgment itself, reports it, and records the commit each check ran on and what changed after it, in the validation record and the pull-request text. (NWQLib 0.99.1: two changes after the release checks, a documentation policy and a one-module fix of archive reopening, needed one full suite on one platform, and the principal judged this only when the user asked.)

- A full suite on a platform reruns for library code that platform's run exercises. A platform's code path is what its run exercises and the other platforms' runs do not, such as a native simulator or a platform-specific dependency; a change to platform-independent code needs the suite on one platform, and a change to an entry point every extension passes through gets it, as at integration.
- The mutation campaign reruns for a change that can lower what the tests detect: a test deleted, trimmed or weakened, a probe added or moved, or a change at a probe site or on the path from its killing test to it. A change that only admits more inputs, or changes text, leaves the campaign's result standing.
- Documentation, notebooks and the version number need only the checks of their own files.

## The review round

- The principal assigns each formal round to fresh reviewers on the advisor models chosen at step 0. The code reviewer covers engineering and the user's workflow, and the mathematics reviewer covers scientific claims and the previous-release comparison. Fresh means independent of implementation and earlier rounds, not a new session for each purpose or correction. One review may cover hand-in, acceptance and the round when its actual scope covers them. Broader integration review focuses on interactions and changed public workflows, using applicable local evidence. Reviewers use the host mechanisms agreed at step 0.
- Each request is a file the reviewer rereads, self-contained: the operating rules (what to read first, the checked runner with its literal command words, the write and Git restrictions, workload limits, that it does not operate the other vendor's app, and that recorded outcomes are hypotheses to test), a fixed review ref of its own, the interfaces to exercise, one combined workflow, the interruption boundaries, the comparison protocol, the output file, and a coverage-gaps section for the report. The request is neutral: revision, scope, recorded decisions, environment and output, without the implementation working files, the worker reports or the advisor's answers. The counselor checks the requests before they go out ([counselor.md](counselor.md)). When a rule changes, the principal changes the request file as well as telling the reviewer. (NWQLib 0.99, when each review ran in a session of its own: the file that session reread still gave it control of the vendor app after the rule had changed, because the change had reached it only as a message, and the user had to shut the session down.)
- Include a targeted sweep when the changed contract or earlier findings expose a shared failure mechanism. For changed per-item counts or chunk layouts, inspect admission timing, storage growth and the consumers of the counted or associated data. A brief that allows two layouts names the law under each. Choose probes from supported public behavior and relevant workloads, distinguishing a synthetic fixture from an uncommon valid input ([triage-calibration.md](triage-calibration.md)). A fix round uses the previous pin as its range base and states the behavior each changed detector must observe.
- The review has a ref that nothing moves. A checked runner that resolves a named ref on every call would let a concurrent integration change the code under review.
- The reviewers use the project's review workflow, such as `scientific-library-review` with the project's review profile, under the scope restrictions below, including that closed items are not reported, in place of a disposition for each finding.
- Shared context stays minimal. A reviewer reads the current scope, decisions, environment, affected source and consumers, primary sources and applicable independent evidence. Producer claims and plan derivations are not their own proof. Earlier independent qualification can be reused when its conclusion, premises and consuming paths still match. Keep implementation discussion out of independent review context.
- The principal merges material findings and checks their witnesses against the affected revision, environment and consumers. Reuse applicable independently observed failures. Rerun a witness when its relevance or evidence remains uncertain, rather than treating a severity label as proof. Send substantive triage to the counselor. Code-fix verification returns to the assigned reviewers, with a fresh reviewer only when the current thread cannot continue. Authorized local documentation corrections close under the documentation route.
- A finding gives its severity, file and line, a witness, the smallest change and an impact sentence: who meets it in ordinary use and what goes wrong for them. Every mathematical finding comes with a complete derivation from the mathematics reviewer.
- A review of fixes checks only what changed, the other places stating the same claims and the context needed to judge them. Give the existing reviewer the delta, findings and new evidence; compare meaning with the pre-correction version to catch cumulative drift. Keep prior qualification where its premises still apply. Reopen a closed item only for new evidence, changed premises or a changed consuming path, and name that reason. New defects in the changed surface remain actionable; optional style preferences do not prolong the round.
- Report material findings and coverage limits. Already closed items need no repeated narrative unless their basis changed. If nothing is actionable, say so with the reviewed scope and any unverified boundary, linking existing evidence rather than rewriting it.
- A reviewer writes its report to the file its request names. Where the host refuses subagents such writes, the request says to return the complete report as the final message, and the principal saves it unchanged.

## From the user's side and against the previous release

- The assigned code reviewer covers the end-to-end user workflow in the first and final formal rounds. It starts from the guide and notebooks, uses the public API, and completes the relevant workflow through results and save/load. Compare ordinary workloads across the current revision, first-review revision and previous release for changed refusals, results, time and memory, using the approved comparison protocol and still-applicable baseline evidence. This purpose can share the formal review session.
- The user-side review has a usability section: it re-walks the previous release's example workflows as a scientist would, reads a public-signature diff against the previous release that the principal generates mechanically before the round, counts the concepts a user must learn per feature family, judges the readability of every new refusal, and lists refactoring proposals as a triage decision item, decided by the library's state: before a release they are welcome, after it only rarely used parts change freely and common paths need the user.
- The user-side review also reports the cost of the user's stated end-to-end problems at this revision, in time, memory and refusals, because a review of the contract alone accepts workloads no user would run. (NWQLib 0.99.1: three rounds accepted a scan over 4^14 sign patterns, which the principal's own end-to-end example then exposed.)
- The assigned mathematics reviewer independently checks the cumulative scientific change against the previous release in the first and final formal rounds. Preserve this cumulative scope, using the round's session rather than opening another solely for that purpose.

## Fix rounds

These rounds handle unresolved substantive findings. Authorized local documentation corrections close within the existing review; they do not enter a new fix round.

- After each review the principal presents the findings item by item with its triage, checked by the counselor, and the user decides.
- A material limitation a reviewer finds is a triage item, including pre-existing or late findings. The user decides whether to fix or defer it, or the principal and counselor under the user's delegation. Optional style preferences are not limitations.
- New or unsupported mathematical findings go to the mathematics advisor before dispatch. A correction already established by applicable qualification reuses that evidence.
- Engineering findings go to code workers by module, and each fix changes every place that states its claim.
- A detector is added only for a public contract or where the review names one. It must fail when the fix is undone, on the path where the defect lives. Before a test is deleted or trimmed, check against the mutation results that it is not the only detector of some probe.
- When a fix replaces a validation with a cheaper one, the verification request asks the reviewer to enumerate, in its first pass, the input classes the old validation covered, rather than rerun only the finding's witness. (NWQLib 0.99.1: two verification rounds each found the next input class the replacement mishandled.)
- A reviewer's smallest change is smallest for one finding. Judge the accumulated chain at every partial, as the circuit breaker says; when the chain has become a design change, the mathematics advisor derives the alternatives and the counselor takes the decision with the principal.
- Steps 2 to 6 follow.
